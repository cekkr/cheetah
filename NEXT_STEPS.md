# Command surface: collapse the repeats into micro-commands, keep the names as aliases

The protocol grew one feature at a time, and it shows: 51 dispatcher commands (the count at the time
this was written; the surface has not shrunk — fourteen of them are now *aliases* over `JOB` and `DEL`,
which is the point: nothing was taken away), of which a large
minority are **the same operation in a different envelope**. The cost is not code size, it is
meaning — `PAIR_SUMMARY`, `GRAPH_DEGREE` and `GRAPH_QUERY … RETURN count` all mean "count without
hydrating", and nothing in their names says so, so a caller picks by memory instead of by intent.
[`README.md`](README.md#telling-the-look-alikes-apart) now documents each command's meaning and the
look-alike distinctions; this entry is the plan to make the surface itself say them.

## What actually repeats

| Repeated shape | Commands | What differs | Status |
| --- | --- | --- | --- |
| **async envelope** | `PAIR_REDUCE_ASYNC/_STATUS/_FETCH`, `PREDICT_INHERIT_ASYNC/_STATUS/_FETCH`, `GRAPH_RECALL_ASYNC/_STATUS/_FETCH` | nothing but the job manager they poll — the first two started as independent implementations with slightly different response fields | **done** — one `JOB` envelope, one manager ([`jobs.go`](src/jobs.go)); all three trios are aliases |
| **batch envelope** | `GRAPH_EDGE_SET` vs `_SET_BATCH`, `PREDICT_INHERIT` vs `_BATCH`, `PAIR_SET` vs `PAIR_PUT_BATCH` | one item inline vs `items=<base64 json[]>`; the per-item work is identical | **done** — one `BATCH <COMMAND> items=…` over any command ([`batch.go`](src/batch.go)); the three `*_BATCH` names stay as-is because their responses are a wire contract, but no fourth should be added |
| **one walk, four hydration levels** | `PAIR_SCAN` / `PAIR_SUMMARY` / `PAIR_REDUCE`, and `GRAPH_NEIGHBORS` / `GRAPH_DEGREE` / `GRAPH_NEIGHBOR_TYPES` / `GRAPH_QUERY … RETURN count` | how much of each visited entry is read and what is emitted: names, a count, an aggregate, full payloads | open — the next step |
| **one erasure, six spellings** | `DELETE`, `PAIR_DEL`, `PAIR_PURGE`, `GRAPH_NODE_DEL cascade=`, `GRAPH_EDGE_DEL`, `RESET_DB` | only the selector (one key, one name, a prefix, a record + its indexes, a directory) — the verb is the same verb | **done** for five of six — one `DEL` with the selector in the arguments; `RESET_DB` stays front-end scoped |
| **point read / point write** | `PAIR_GET`/`PAIR_SET`(`_HIDDEN`), `GRAPH_NODE_GET`/`_SET`, `GRAPH_EDGE_GET`/`_SET`, `PREDICT_SET` | which namespace the key lives in, and whether one flag bit is set | open |
| **placement read** | `CLUSTER_STATUS` vs `FORK_ASSIGN` | whole map vs one prefix — a selector, not a command | open |

Three argument dialects sit on top of that (positional for KV/`PAIR_*`, `key=value` for
`GRAPH_*`/`PREDICT_*`/`CLUSTER_*`, a clause language for `GRAPH_QUERY`), so two commands doing the
same thing often cannot even be written the same way.

## The decomposition

Factor every command into three orthogonal parts and give each part its own token:

```text
<verb>  <target>            <view / modifiers>
GET     pairs|graph|values  ─
SET     …                   hidden=1 · items=<base64 json[]>
DEL     …                   cascade=1 · recursive=1
SCAN    …                   view=names|count|stats|types|payload:<reducer> · limit/cursor/depth
JOB     submit|status|fetch  ─  (one envelope over any bounded SCAN/SET)
```

- **`SCAN` with a `view=`** absorbs `PAIR_SCAN`/`PAIR_SUMMARY`/`PAIR_REDUCE` and
  `GRAPH_NEIGHBORS`/`GRAPH_DEGREE`/`GRAPH_NEIGHBOR_TYPES`. They already share the walk in code —
  `PairScanWithOptions`, `walkPairSummary` and `reduceWithPayload` differ in their accumulator, which
  is exactly what `view=` would select. `view=payload:<reducer>` reuses the existing reducer registry
  ([`reducers.go`](src/reducers.go)), so the extension point stays where it is.
- **`JOB`** replaces the two original async trios and now backs the third: `JOB submit <any bounded command>` → `job=<id>`, then
  `JOB status <id>` / `JOB fetch <id>`. One job manager, one progress contract, and any future
  long command (`GRAPH_RECALL_ASYNC` is the first shipped example) gets an async form for free instead
  of a third copy of the same three commands.
- **`items=`** as a modifier rather than a `_BATCH` command name; the single-item form stays as the
  degenerate case.
- **`DEL` with a selector** covers all five erasures, with the scope explicit in the arguments
  (`DEL values key=<n>` vs `DEL pairs prefix=<p> payloads=1` vs `DEL graph node=<id> cascade=1`)
  instead of implied by the verb's name. This is where meaning is lost most often today.
- **Leave `GRAPH_QUERY` alone.** Its clause language is a genuinely different surface, not an
  envelope; folding it into `SCAN` would trade one clear grammar for a pile of flags. `GRAPH_RECALL`
  and `GRAPH_SIMILAR` likewise: they are distinct operations, not views.

## Recomposition as aliases — the compatibility half

Nothing above is worth breaking a client for. Every current name stays, re-expressed as an **alias**:
a legacy command name plus an argument rewriter plus a response formatter, registered at startup in
one table the way `registerDefaultReducers` registers reducers. `ExecuteCommand` resolves the alias,
runs the micro-command, and renders the legacy response.

Two constraints make the formatter non-optional:

- **Response field names are a wire contract.** `purged=`, `matches=`, `degree=`, `count=`,
  `next_cursor=`, `job=` are parsed by external clients (the Python adapter in
  `/Users/riccardo/Sources/GitHub/lmdb` reads them positionally in places). An alias must reproduce
  its legacy response byte-for-byte; only the internals change.
- **One command, one line.** The single-line rule applies to micro-commands and aliases alike;
  list-shaped output still travels as `payload=<base64>`.

Aliases also become the place where the three argument dialects are absorbed: micro-commands accept
`key=value` only, and the positional forms survive exclusively inside the alias rewriters
(`PAIR_SCAN <prefix> <limit> <cursor>` → `SCAN pairs prefix=… limit=… cursor=…`).

# Done (implemented + verified by tests — do not re-add):
- **Adaptive main-key slots remove the single-file insert choke point when concurrency warrants it.** `sharded_key_slots` is off by default; when enabled, the allocator begins with one randomly chosen lane and activates another only while every active lane is leased, so serial loads retain one dense file and contention grows the shard count. A lane owns its sequence high-water mark, `main_keys_<slot>.table`, and `main_keys_<slot>.recycle.table`; leases are single-holder, slot-local deleted rows are reused first, and all files remain O(1) offset-addressed. `main_keys.format.dat` pins the flag and `key_slot_bits` (1..16, default 12) and refuses incompatible reopens. The existing pair entry stores an absolute key in 6 bytes, so the implemented split deliberately stays inside that immutable 48-bit envelope (`[slot:n][sequence:48-n]`) instead of silently truncating the requested 64-bit form; at 12 bits this is 4,096 lanes × 2^36 rows. Both binders accept the settings. On the same 3-second, 64-worker mixed harness, a fresh comparison measured about 14.5k total QPS sharded versus 12.6k unsharded (~15%); the benchmark toggle is `CHEETAHDB_BENCH_SHARDED_KEYS=1`. Verified by `TestShardedKeySlotsConcurrentInsertReadPairAndReopen`, `TestShardedKeySlotLeasesAreExclusive`, `TestShardedKeySlotsRecycleWithinTheirOwnFiles`, `TestKeySlotFormatIsCreationTimeAndGuardsLegacyData`, the engine-settings test, and both binder admin suites.
- **The association-cache capacity counter now heals itself after a reopen.** Startup stays lazy (no blocking namespace scan), but every maintenance sweep counts the live `l/` and `q/` rows it retains; when a full lap wraps without a concurrent external cache mutation, that census atomically replaces the process-local estimate. The maintainer's immediately following aging page therefore sees the restored count and applies `capacity` without an operator first issuing `GRAPH_CACHE stats recount=1`; an invalidated lap simply retries. Entry adjustments clamp at zero, and `DEL graph_cache scope=links|queries` now subtracts only what it removed instead of zeroing the still-live family. Verified by `TestGraphCacheSweepRecountsAfterReopenAndEnforcesCapacity`, `TestGraphCacheSweepCensusRetriesAfterConcurrentMutation`, `TestGraphCacheScopedDeletePreservesRemainingEntryCount`, the full graph-cache suite, and focused `-race` runs.
- **Live, persistent per-database cache tuning.** `DB_CONFIG <name> [key=value …]` now updates an existing database without retargeting the connection. Payload-cache and graph-association-cache settings apply hot when the handle is loaded, report under `on_open=` otherwise, and persist in `<db>/settings.ini`; trie geometry is accepted but reported under `reset=` because `pairs/format.dat` still wins until `RESET_DB`. `GRAPH_CACHE config` writes the same settings file, so its complete profile survives a reopen. The payload cache keeps a stable pointer while its limits change, allowing a disabled cache to be re-enabled safely; focused tests now pin copy isolation, eviction, disable/re-enable and concurrent resize under `-race`. Both binders expose `configureDatabase` / `configure_database` and the action lists. Verified by the `TestDatabaseConfig*`, `TestGraphCacheConfigPersistsThroughDatabaseSettings`, and `TestPayloadCache*` Go tests plus both binder suites.
- **Async recall for wide fan-outs, retrievable by job id.** `GRAPH_RECALL` is now a registered `jobCommand`, so `JOB submit GRAPH_RECALL …` returns `graph_recall_<n>` and the same id is accepted by `JOB status id=…` / `JOB fetch id=…`. The convenience aliases `GRAPH_RECALL_ASYNC/_STATUS/_FETCH` use that exact manager; there is no third async implementation. A detached recall with no explicit `budget=` gets the maximum bounded sweep (262 144) instead of the interactive default (4 096), while an explicit limit remains authoritative. Progress counts the expansion/hydration budget consumed and closes at 100% when the frontier finishes early. `GRAPH_RECALL_FETCH` renders the normal recall response; generic `JOB fetch` retains `job=` for correlation and consumes the id. Both binders expose submit/fetch/await helpers that return and accept the id. The shared result path also fixed an old nondeterminism: equal-activation seeds now choose `via` lexically, so identical sync/job recalls are byte-stable. Verified by `TestGraphRecallJobsAreRetrievableByID`, the per-kind sequence test, repeated graph tests, and both binder suites.
- **A byte-wise protocol over TCP: the command as a 2-byte index, values in their own type.** The text protocol describes everything as a string — `42` is two bytes, `0.25` four, a 32-byte key sixty-four in hex, the command name up to twenty-three — which is pure overhead on a wire that is already round-trip bound. A TCP connection can now speak **frames** instead ([`src/binary_protocol.go`](src/binary_protocol.go)): `0xC7`, a type byte, a length, then a command index and typed arguments (string, bytes, uint, int, float, bool, an enumeration id, or *null* meaning "this modifier is absent"). A binary connection declares itself by its first byte, which no text command can start with, so there is no negotiation to get wrong and no port to add.
  **It is a codec, not a second command surface, and that is the whole design.** A request frame decodes into the *canonical command line* and continues down the ordinary path; the answer line is re-encoded into a response frame. So the binary layer knows nothing about the commands it carries and never needs editing when one is added — the same property that makes `BATCH` general. Response fields are typed automatically by a rule that needs no per-command table: a value that re-renders *identically* from an integer is an integer, from a float a float, everything else a string, which is what guarantees a client re-rendering the frame gets the original line byte for byte. The canonical line therefore stays the contract, and its limits still bite: a `key=value` value may not contain whitespace, and a frame that would produce one is refused rather than truncated (the `bytes` type is the way out, and it is free here). The one relaxation is the last positional argument, which may contain spaces because in the line it *is* the rest of the line — what `INSERT`, `EDIT` and `PAIR_SET` treat it as.
  **Widths come from four places, most specific first:** the type tag (an explicit 1…8, which never depends on anything else), the table's profile, the session defaults from the handshake, then 8/8/8. The table profile is persisted per database (`protocol_profiles.dat`, [`src/binary_profile.go`](src/binary_profile.go)) rather than declared per client, because two processes writing the same table must encode it the same way; it applies to the arguments *after* `table=` in a frame, since arguments decode in order and the table is not known before it is read.
  **`ALIAS` is the part of the protocol that describes the protocol** ([`src/micro_alias.go`](src/micro_alias.go), [`src/command_index.go`](src/command_index.go)). The command index is *derived* from the same three tables `ExecuteCommand` consults — micro-commands, aliases, the switch names — so adding or removing an alias does not ask anyone to update a second list, and the ids are explicitly **not** a stable wire contract the way response field names are. What makes them safe to use is a digest: `ALIAS digest` is sixteen characters, and the handshake ack hands over the digest, the epoch and *both tables in full*. That last part is a necessity, not an optimisation — a response names its fields by index, so a client without the argument-key dictionary could not read even the answer to `ALIAS keys`. `ALIAS list`/`get`/`keys`/`types`/`profile` cover the rest, `profile` doubling as the read/write of a table's widths.
  The TCP front-end grew a `connSession` so the text and binary loops share one dispatch ([`src/server.go`](src/server.go)) — `DATABASE`/`RESET_DB` work over binary because of it, and there is no second copy to drift. A malformed frame answers `ERROR` and keeps the connection; only a frame that cannot be *delimited* closes it, because past that point nobody knows where the next one starts. Verified by [`src/binary_protocol_test.go`](src/binary_protocol_test.go): the index covers every registered name (and a source scan catches a switch command missing from `builtinCommandNames`), the digest is stable across a rebuild, request decoding for every type, the table profile changing what the same bytes mean, response round-trips that must return the exact line, and an end-to-end exchange over a real socket. Both binders implement it ([`binders/nodejs/lib/binary.js`](binders/nodejs/lib/binary.js), [`binders/python/cheetah_db/binary.py`](binders/python/cheetah_db/binary.py)) as a transcoder over the lines their command layers already build, so `kv`/`graph`/`records`/`predict`/`admin`/`CheetahDatabase` run over binary unchanged — `new CheetahClient({binary: true})`, `CheetahClient(..., binary=True)`.
  Learned the hard way, and pinned by a test in both binders: a client must **state every width explicitly** when transcoding. A float written 8 bytes wide but tagged "use the default" is read back at a 4-byte session width and comes out as `1.625`; the transcoder cannot know which table an arbitrary line addresses, so it cannot predict what a width-0 tag resolves to. Width 0 is for a caller that has loaded the table's profile and means it.
- **One `BATCH` command instead of one `*_BATCH` name per family.** Bulk ingest is bound by the round trip — the server idles around a quarter of a core while the client waits on latency — and the answer had been a dedicated command per family: `PAIR_PUT_BATCH`, `GRAPH_EDGE_SET_BATCH`, `PREDICT_INHERIT_BATCH`, each with its own `items=` parser, counters and response shape, with a fourth due every time another command got hot. `BATCH <COMMAND> items=<base64 json[]>` ([`src/batch.go`](src/batch.go)) is that idea once: it builds one line per item and hands each to `ExecuteCommand`, so it targets *any* command the router resolves (micro-commands, aliases and the historical switch alike) and needs no edit when a command is added. Registered as a micro-command, so `BATCH` is resolved before the switch like `DEL`/`JOB`/`RECORD`.
  Items come in three shapes because the protocol has two dialects: a JSON string is a raw argument line, a JSON array is positional arguments, and a JSON object is the `key=value` dialect layered over the *shared* modifiers — any `key=value` on the `BATCH` line that is not one of its own, so `BATCH GRAPH_EDGE_SET type=knows items=[…]` writes the edge type once instead of ten thousand times. Execution is sequential on purpose: the cost being removed is the round trip, not the lock, and parallelism would change the order two writes to one key are applied in. Not a transaction, so the reply is a `SUCCESS` carrying `requested`/`applied`/`failed` and `first_error=item_<n>:<reason>`; `continue_on_error=1` keeps going past a bad item. `results=1` is the **default** — a batch of reads is useless without them — and returns each item's own response line in `payload=`, positionally aligned, `null` where an item never ran; a line that is not valid UTF-8 (only `READ` of a binary payload) would be silently corrupted by `encoding/json`, so the whole array switches to base64 and declares `results_encoding=base64`.
  **The job half is what makes a long batch usable.** `async=1` (or `JOB submit BATCH …` — the same path, `BATCH` is a registered `jobCommand`) answers with a `job=<id>`, and the new `JOB results id=… from=… limit=…` pages through the response lines *already produced* without consuming the job, while `JOB fetch` stays terminal and stays the aggregate. That required one addition to the job manager — `microJob.appendPartial`/`partialsFrom` ([`src/jobs.go`](src/jobs.go)) — and `available=` is emitted in `JOB status` only when partials exist, so the byte-for-byte responses of `PAIR_REDUCE_STATUS` and `PREDICT_INHERIT_STATUS` are untouched. `BATCH` refuses `BATCH`/`JOB` as targets (recursion) and the three front-end-scoped names.
  Verified by [`src/batch_test.go`](src/batch_test.go): raw-line items really run the same `PAIR_SET` the single command does, object items inherit and override the shared modifiers, failures are counted without aborting the request (and abort leaves `null` in the aligned payload), the forbidden targets, the synchronous validation of a malformed request, `results=0`, the detached form streamed page by page to completion, and `JOB submit BATCH`. Both binders wrap it ([`binders/nodejs/lib/batch.js`](binders/nodejs/lib/batch.js), [`binders/python/cheetah_db/batch.py`](binders/python/cheetah_db/batch.py)) and add automatic batching: the Node client folds a burst of one command issued in a single turn of the event loop into a `BATCH` transparently (a sequential caller never has two outstanding, so it never batches and pays nothing), while the Python client — synchronous, one command in flight — defaults to *reporting* the opportunity and offers `with client.batching():` and `auto_batch={"mode": "deferred"}` to take it.
- **Multi-field record tables, with per-field byte widths and live schema changes.** A pair name maps to one payload, so describing one thing with several quantities meant several names — `cnt:<k>`, `prob:<k>`, `meta:<k>`: three trie entries, three payloads, three round-trips, and nothing keeping them consistent. `RECORD` ([`src/micro_record.go`](src/micro_record.go)) declares those quantities once as fixed-width fields (`define table=ngram fields=cnt:uint:4,prob:float:4,label:string:12`) and packs them into a single row. Rows are ordinary payloads under the reserved `\x06rr:<table>/<generation>/<key>` prefix ([`src/record_table.go`](src/record_table.go)), so they inherit the payload cache, slot recycling and the paged trie walk unchanged; the schema is a fixed-byte `"CHRS"` file per table ([`src/record_schema.go`](src/record_schema.go)), not JSON, in keeping with the prediction tables.
  **The evolution contract is the point, and it rests on one invariant: offsets never move.** `alter add=` appends the new field at the current row width; `alter drop=` removes the field from the schema and leaves its bytes where they are. Neither rewrites a row. A row written under any past schema therefore decodes correctly under the current one, and a row shorter than `RowWidth` is exactly a row that predates an ADD — its missing tail fields read `null`, never a zero nobody wrote, and the next `RECORD set` brings it up to full width. The cost is dead space after a drop, which `RECORD compact` reclaims: it copies every row into generation+1, renames the schema file into place, and only then purges the old generation, so an interrupted compaction leaves the old layout intact rather than half a table converted (it also purges the target prefix first, so leftovers of a previous interruption cannot be mistaken for fresh rows). A rewritten row is truncated at the last field the source actually had, so compaction does not turn "never written" into zero either.
  `RECORD set` writes only the fields named and is serialized per row by a stripe lock — it is a read-modify-write, and two concurrent sets would otherwise drop each other's fields. Deletion stayed with `DEL` (`DEL records table=… key=…`, `drop=1` for the whole table), since that is the protocol's only erasure verb. Also extracted while doing it: `getPairPayload`/`upsertPairPayload`/`deletePairAndPayload` in [`src/commands.go`](src/commands.go), which the graph helpers now delegate to instead of owning. Verified by [`src/record_test.go`](src/record_test.go) — lifecycle and partial update, stale-row `null` after an ADD, offsets undisturbed by a DROP, compaction (values preserved, `null`s preserved, old generation gone), prefix+cursor paging, `DEL records` both ways, schema round-trip across reopen, and every type at every declared width.
  Not built, deliberately: no secondary index over field values (scan filters on the row key prefix) and no reducer mode that reads fields. Both binders wrap the family ([`binders/nodejs/lib/records.js`](binders/nodejs/lib/records.js), [`binders/python/cheetah_db/records.py`](binders/python/cheetah_db/records.py)), validating a field declaration — type, width, reserved name — before it reaches the wire.
- **Creating a database over the wire, with settings of its own.** `DATABASE <name> key=value` already recorded per-name overrides, but they lived in an in-memory map: a database "created with ad-hoc settings" silently reverted to the server's `[database]` defaults at the next restart, and there was no way to *create* one — `DATABASE` opens-or-creates, so a typo adopted a populated directory instead of refusing. Now `DB_CREATE <name> [key=value …]` creates and refuses an existing name, `DB_LIST` reports every database with the settings it would open with (and whether it carries overrides of its own), and every override — from either command — is written to `<data_dir>/<name>/settings.ini` and re-read at each open, layered defaults → file → session ([`src/engine.go`](src/engine.go), [`src/config.go`](src/config.go)). Trie geometry is unaffected by design: `pairs/format.dat` still wins on reopen, so adopting a new stride still means `RESET_DB`.
  Both commands live in `engineControlCommand`, called by the CLI and the TCP loop alike — they address the *registry*, which a `Database` handle cannot see, but they are not connection-scoped either, so duplicating them in the two front-ends the way `DATABASE`/`RESET_DB` are duplicated would have been two implementations to keep in step. Fixed on the way: a database name is now validated as a single path component (`validateDatabaseName`), because `RESET_DB ../..` resolved against `data_dir` and deleted outside it. — [`src/engine_control_test.go`](src/engine_control_test.go), including the restart that proves the settings outlive the process.
- **The jump store stopped reopening its files on every operation.** `jumps.bin` and `index.bin` are
  now opened once per database and held (`ensureJumpStoreLocked` is a one-shot initialiser,
  `closeJumpStore` releases them from `shutdown`), the append offset lives in memory instead of being
  re-derived with a `Seek(0, SeekEnd)` per write, resolved nodes sit in a `jumpCache` LRU, and the
  `.jump` legacy fallback is only attempted when such files were actually present at open. ID
  allocation for both jumps and pair tables reserves a block and persists its **end** before handing
  out the first id in it, replacing a full `os.WriteFile` per allocation — a crash can burn unused
  ids but can never re-issue a live one (`TestJumpIDsNeverRepeatAcrossReopen`).
  The profile that prompted this: on a 4 000-edge `GRAPH_EDGE_SET_BATCH` ingest, `syscall.syscall`
  was 80% of CPU and `os.OpenFile`/`os.Open` alone 53%, all under `loadJump`/`createJump`/`writeJump`.
  Cost per edge went **19.4 ms → 0.54 ms** (`CHEETAH_GRAPH_TERM_INDEX=0`, macOS/APFS), and the
  image-sign-db ingest that motivated it went from 95 s to 6.7 s per image. Covered by
  [`src/jump_store_test.go`](src/jump_store_test.go) — id reuse across reopen, cache coherence across
  rewrite/delete, and the legacy-file backfill.
  Known, pre-existing and untouched: `deleteJump(1)` does not hide jump id 1, because
  `loadJumpFromIndexLocked` still reads a raw offset of 0 for that one id as "the very first jump"
  rather than as the missing marker.
- **Equal-size `INSERT`s now reserve distinct value slots before the asynchronous write.** Each
  `ValuesTable` seeds an atomic high-water mark from its file once at open and `ReserveEntry`
  advances it before `WriteAt` queues bytes. `getAvailableLocation` still consumes recycled slots
  first, then asks value tables for a fresh reservation; it no longer re-stats a file that the
  writer has not grown yet. The live failure was three acknowledged six-byte inserts all pointing
  at `EntryID 0` and all reading the last payload; after the fix they occupy three slots and remain
  distinct after close/reopen — `TestEqualSizeInsertsReserveDistinctValueSlots`
  ([`src/key_recycle_test.go`](src/key_recycle_test.go)).
- **Concurrent `PAIR_SET` no longer loses acknowledged mappings.** All pair-trie mutations now share
  `pairMutationMu`: insert and delete both split/promote jump nodes and rewrite common ancestors, so
  protecting only purge-side deletion left multi-connection writers racing. The live DB-SLM-shaped
  repro acknowledged 512 writes under `cnt:1:` but retained only 57; the regression test now
  inserts 256 shared-prefix keys concurrently and verifies every point read plus the full scan on
  both strides — `TestConcurrentPairSetSharedAncestors`
  ([`src/pair_scan_test.go`](src/pair_scan_test.go)).
- **Micro-commands, first two verbs: `JOB` and `DEL`, with every legacy name kept as an alias.** The decomposition described above now has its machinery: a micro-command registry ([`src/micro_command.go`](src/micro_command.go)), an alias table ([`src/command_alias.go`](src/command_alias.go)) and a registry of commands runnable inside `JOB` ([`src/jobs.go`](src/jobs.go)), all three built once by `ensureCommandRegistries` the way `registerDefaultReducers` builds the reducer registry. `ExecuteCommand` consults micro-commands, then aliases, then its own switch; a name that lives in the first two no longer has a switch branch, so there is exactly one implementation per command.
  **`JOB`** (`submit`/`status`/`fetch`, [`src/micro_job.go`](src/micro_job.go)) replaced the two job managers with one. `reduce_jobs.go` and `predict_jobs.go` are deleted; a `microJob` carries state, `completed`/`total`, named counters and a *structured* result (`[]microField`), which is what lets one manager serve families whose response fields differ. Ids keep a **per-kind** sequence (`reduce_1`, `predict_inherit_1`, `graph_recall_1`) — a shared counter would renumber ids a client may have stored. Adding an async form to a new long command is one `jobCommand` registration, as `GRAPH_RECALL` now demonstrates.
  **`DEL`** ([`src/micro_del.go`](src/micro_del.go)) is one erasure verb with the scope written out: `DEL values key=`, `DEL pairs key=`, `DEL pairs prefix=… [payloads=0|1]`, `DEL graph node=… [cascade=1]`, `DEL graph from=… to=…`. It also gained something no legacy spelling could say — `payloads=0` unlinks names from the trie and leaves the values addressable by absolute key (`PairPurgeWithOptions`). `RESET_DB` deliberately stays out: it is front-end scoped because it changes what the connection points at.
  **Compatibility is pinned, not asserted.** Expectations were captured from a server running the pre-refactor code and only then re-run against the aliases: all eleven legacy names (`DELETE`, `PAIR_DEL`, `PAIR_PURGE`, `GRAPH_NODE_DEL`, `GRAPH_EDGE_DEL`, `PAIR_REDUCE_ASYNC/_STATUS/_FETCH`, `PREDICT_INHERIT_ASYNC/_STATUS/_FETCH`) answer byte for byte what they answered before, success and error paths alike, including `DELETE` on an unwritten row still answering `ERROR,key_not_found` *and* propagating `io.EOF`, and the async fetch still mirroring the synchronous line exactly — `TestLegacyDeleteAliasesAreByteIdentical`, `TestLegacyReduceJobAliasesAreByteIdentical`, `TestLegacyPredictJobAliasesAreByteIdentical`, `TestJobIDSequencesStayPerFamily` ([`src/command_alias_test.go`](src/command_alias_test.go)), plus `src/micro_command_test.go` for the new surface; green under `-race`. Two details worth keeping: an alias formats only success and `PENDING` (error tokens are deliberately the same words, with a small `ErrorTokens` remap where `JOB` says `job_not_found` and the trios said `reduce_job_not_found`), and binary values cross into the micro dialect as `x<hex>` — it splits tokens on whitespace, so a pair key with a space survives no other way.
- **`PREDICT_*` failures now carry the `ERROR,` prefix.** `handlePredictTrain`/`handlePredictInherit` and friends returned `err.Error()` verbatim, so a failed inherit answered a bare `prediction_entry_not_found` — neither success nor error to a client classifying on the prefix, while every other family prefixed its failures. Fixed at the dispatcher boundary (`normalizeCommandResponse`, [`src/database.go`](src/database.go)) rather than handler by handler, so it holds for every present and future handler: any response opening with none of `SUCCESS`/`ERROR`/`PENDING` becomes `ERROR,<reason>`. This is client-visible, which is why it shipped with the alias work — `TestPredictFailuresCarryTheErrorPrefix`, `TestNormalizeCommandResponse`.
- Deleted keys are reused. A `DELETE` on a key in the middle of `main_keys` used to leak its row for the life of the database: only the *highest* key came back, via `findNewHighestKey` walking the counter down. Freed rows now go on a `main_keys.recycle.table` free list, which `persistPayload` pops before falling back to the counter (`nextKey`/`releaseKey`, [`src/helpers.go`](src/helpers.go)). Consequences worth knowing: `highestKey` is now a **high-water mark that never descends**, so `loadHighestKey` restores it from the file size in O(1) instead of scanning backwards over trailing tombstones — and it has to, because the old "highest live key" answer would restart the counter underneath rows the free list has already claimed and hand them out twice. `findNewHighestKey` is gone with it. A database upgrading from before the free list gets its already-deleted rows collected once, on first open, by a blocked sequential pass over `main_keys` (`seedKeyRecycle`, logged at INFO); without it the feature would only ever reclaim keys deleted *after* the upgrade. `Delete` also zeroes the row *before* pushing either free list, so a failure half-way leaks a row instead of handing out a row that is still live, and the failed-write path in `persistPayload` returns the key to the free list rather than decrementing the shared counter, which could previously hand a live row to the next inserter. — `TestDeletedKeysAreReused`, `TestKeyReuseSurvivesReopen`, `TestKeyFreeListSeededFromExistingDatabase`, `TestConcurrentInsertDeleteNeverHandsOutALiveKey` (`src/key_recycle_test.go`), green under `-race`; end-to-end over TCP, 5 deleted keys came back to the next 5 inserts and the sixth resumed at the high-water mark.
- `RecycleTable` no longer wraps at 65,536 entries, and serves both free lists. The depth counter was a `uint16` at offset 0 that `Push` incremented unchecked: entry 65,536 rolled it to zero, `Pop` declared the list empty, and 64Ki recorded slots leaked while the values table kept growing. The file is now self-describing (`"CHRL"` magic, version, entry size, `uint64` depth in a 16-byte header) and the same type backs both the value-slot list (5-byte entries) and the key list (8-byte entries). Legacy headerless files are migrated in place on open, carrying their entries over, rather than being refused or dropped. The depth is held in memory and only the 8 changed bytes are rewritten per mutation, so `Pop` costs one read plus one write instead of the two reads plus a write it used to; the ordering is chosen so a crash always leaks a record rather than handing one out twice — `TestRecycleTableHoldsMoreThanTheLegacyCap`, `TestRecycleTableMigratesLegacyFile`.
- `ValueLocationIndex.Encode` no longer truncates the table id. It wrote the id with `PutUint32(buf, TableID)` and then overwrote `buf[3:5]` with `EntryID`, so the id's low byte was destroyed and every location decoded as `TableID / 256` — 1 through 255 all read back as 0. It was latent only because the first table holds 65,536 entries: the moment a size class opened `values_<size>_1.table`, its reads were served from table 0. Now written as a plain 3-byte field, with `getAvailableLocation` refusing to allocate past `MaxValueTableID` instead of silently truncating. Databases that never passed one table per size class are byte-identical before and after — `TestValueLocationRoundTrip`.
- `PAIR_PURGE` race (lost and stranded entries): pair-trie mutation is serialized by the same
  `pairMutationMu` now used for inserts. `deletePairValue` holds it for the whole `deletePairAt`
  walk, so node collapse, jump promotion and `deletePairTable`'s `os.Remove` cannot interleave
  between goroutines deleting keys that share an ancestor. `purgePairEntries` keeps its fan-out
  unchanged and the expensive half — `Database.Delete` of the payload — remains parallel. Before:
  8 keys under one prefix failed **5 of 8 trials** over TCP; after: 24 of 24 trials clean —
  `TestPairPurgeSharedAncestors` ([`src/pair_scan_test.go`](src/pair_scan_test.go)), both strides,
  green under `-race`.
- **Real-time association cache with self-training pruning.** `GRAPH_RECALL` now learns from itself. Every run offers what it discovered to a set of *parallel, implicit tables* under the reserved `\x07gc:` prefix — directed shortcuts `l/<from>/<to>` ("from here you reach there, this strongly") and convergences `q/<signature>` ("what this seed set has in common") — and every later run reads them back for free: a shortcut enters the frontier beside the seeds, so a link that had cost three hops costs zero and the spread restarts from it with the budget intact. `cache=on` is the default and never changes the *shape* of an answer, only what it reaches; `cache=off` restores the previous behavior byte for byte; `cache=serve` also answers a repeated comparison from the stored convergence when the graph has not moved since.
  **It trains rather than fills**, which is the whole point: a pair never seen before is written only *with a probability*, raised by the association's strength, by its distance (an adjacent neighbour is no shortcut — the graph already finds it — so it is damped to 30%) and by the learned bias of that *kind* of query, tracked across 64 shape slots and retuned from each shape's own hit rate. A one-off is almost never stored; something recurrent gets a fresh roll every recall and is admitted nearly for certain. Each row then counts `hits` and `observations` **apart**, whose ratio is the usage probability — the direct measure of whether the row earns its place — and a background maintainer decays utility, drops what falls under threshold, and halves survivors' counters on every completed lap, so the numbers stay small and an old famous row cannot outrank a new useful one forever. The maintainer paces itself on `ResourceMonitor` (skips its turn at CPU ≥ 80/85% or memory pressure ≥ 0.90, sizes its page from `RecommendedWorkers`, stretches its interval up to 32× while idle) and **needs no command**: `GRAPH_CACHE prune` exists only for an operator or a test that wants the result now.
  Staleness is handled by a graph write epoch bumped in `graphUpsertPairPayload`/`graphDeletePairAndPayload` — the single choke point every graph write already passes through, so a *new* write path invalidates stale convergences without having to remember to — persisted at `\x07gc:e` with the same reserve-a-block scheme as jump ids, because resuming from zero after a restart would make a pre-restart convergence read as fresh. Surface: `GRAPH_CACHE stats/config/get/links/common/put/prune` plus `DEL graph_cache [scope=]`, with `put` deliberately bypassing the sampling so a client that paid an expensive comparison *outside* the graph (two descriptors, two colour fields, two image signatures) can make the next search start from the answer. Cache rows are written hidden, so they never appear in a user's scans or summaries — `src/graph_cache.go`, `src/micro_graph_cache.go`, `src/graph_cache_test.go` (18 tests, green under `-race`).
- Associative recall ("hippocampus"): `GRAPH_RECALL` spreads activation from several seed terms at once and returns every node above a requested precision with the seeds that reached it, the conceptual distance, the evidence path (weight + confidence + modality per edge) and a novelty score, so a model can pick what to explore instead of guessing the next query. Activation from different seeds combines in noisy-OR, which makes a node reached by two seeds outrank both single-seed neighbours — `min_sources=2` isolates exactly those convergences. Seeds resolve three ways: exact id, lexical overlap through the new `\x05gt:` term index (maintained on node upsert/delete, rebuildable with `GRAPH_TERM_INDEX action=rebuild`, switchable off with `CHEETAH_GRAPH_TERM_INDEX=0`), and declared synonym edges (`synonym`/`alias`/`same_as`/`aka`/`abbreviation`/`acronym`), which cost a hop but no conceptual distance. `GRAPH_SIMILAR` adds distributional similarity — same neighbours, or same words in the id. Everything is bounded by `branch_limit`/`budget` and degrades with `truncated=1` rather than stalling — `src/graph_recall.go`, `src/graph_recall_test.go`.
- Complete reference sentences now bridge semantic and episodic recall. `GRAPH_NODE_SET references=<base64-json[]>` stores bounded `{id,text,source?,ordinal?}` evidence on a node (omission preserves it, `references=-` clears it); reference words feed the derived term index. `GRAPH_RECALL references=1 [reference_limit=…]` hydrates those sentences plus verbatim payloads named by evidence-path `edge.props.src`, returning them on the ranked association instead of making a client rebuild prose from ids and tokens. Hydration is opt-in and globally bounded (default 32, max 256), so ordinary recall keeps its old IO posture — `TestGraphNodeReferencesRoundTripAndFeedTheTermIndex`, `TestGraphRecallHydratesCompleteNodeAndEpisodeReferences` (`src/graph_recall_test.go`).
- Prefix-overlap trie defects (data loss), all four fixed and pinned by `TestJumpTerminalOverlaps` (`src/pair_adaptive_test.go`) and `TestPairSetGetDeleteRoundTrip` (`src/pair_scan_test.go`), both strides. Terminal, child and jump are independent flags, so lookup/insert/delete settle "does the key end here?" before following a jump; a node does not always start on a stride boundary, so all key walks pick their branch through `selectPairBranch`, which falls back to the 1-byte branch a jump split can leave behind; delete reports emptiness per node (`PairTable.IsEmpty`), not per entry, which is what made it drop live subtrees; and `collectSingleBranchPath` refuses to collapse a path through an entry that is terminal *and* continues. A prefix-free key set is no longer a requirement.
- `PAIR_SUMMARY` deadlock: `walkPairSummary` now enqueues through the same `select` + `default` → inline-drain helper as the scan walk and sizes its queue on the branch fan-out — `TestPairSummaryDrainsSaturatedQueue`.
- Cursor pagination: pages are complete, ordered and resumable. The accumulator keeps the smallest `limit+1` keys above the cursor in a bounded heap and prunes any branch whose path exceeds the largest kept, and the scan walk is ordered (smallest branch first) so it stops at the page instead of aborting at "enough results" — `TestPairScanCursorPagination`. Measured on 20k keys at stride 2: a full pagination at `limit=256` returned 3,344 of 20,000 keys, now returns all 20,000; single-page latency unchanged.

- Idempotent shutdown: `Database.Close`, `FileManager.Close`, `Engine.Close` and `ClusterMessenger.Stop` are safe to call repeatedly — `TestDatabaseCloseIsIdempotent`, `TestEngineCloseIsIdempotent`.
- Adaptive per-node pair-trie indexing: a node whose dense array would exceed `pair_list_max_bytes` stores its entries as a sorted, binary-searched list while sparse and densifies into the direct-mapped array past that budget (optional extra cap via `pair_list_max_fill_percent`, default off); self-describing `"CHPT"` node header, per-database `pairs/format.dat` marker (authoritative on reopen, refuses legacy directories), `adaptive_pair_index` config/env/override switch, and `PopulatedBranchIndices` so enumeration is O(populated) instead of O(branch capacity) — `src/types.go`, `src/tables.go`, `src/pair_format.go`, `src/database.go`, `src/config.go`; `src/pair_adaptive_test.go`, `src/pair_adaptive_bench_test.go`.
